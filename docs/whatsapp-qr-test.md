# WhatsApp QR integration — isolated test stage only

This is an **unofficial** Baileys/WhatsApp Web integration, not affiliated with Meta or WhatsApp. WhatsApp can change its protocol or restrict/ban an account. Use a separate test sender, never the school's live account during this stage. It has no Twilio per-message fee, but internet, server operation and maintenance still cost money. It is not an approved production rollout.

## Safety boundary

* Disabled by default. An authenticated Admin/SuperAdmin must acknowledge the risk and explicitly start the test. A linked session may reconnect after the server restarts, as the same Windows user; it may also need relinking. The school PC/API and internet must be running. The admin window need not stay open.
* The only messages supported are fixed **TEST ONLY** pick-in and drop-out samples to a number entered and consented to by the admin. There is no API for arbitrary content, no real student records and no connection to `IWhatsAppSender` or the existing WhatsApp outbox. Firebase notifications are unchanged.
* **The existing live Twilio/outbox worker is separate and unchanged.** An API/installer restart can release historical Twilio jobs if Twilio is enabled; when disabled, its old dry-run behavior can mark jobs as sent without delivering them. The QR preview build is compiled with its own outbox worker disabled, uses a separate `SmartSchoolQrPreview` LocalDB database and binds to loopback, but it cannot control a separate live API. The preview installer refuses common existing-installation signs and never kills a process using port 5000; those checks cannot detect every possible production setup. Never install the preview on a live school server or import production data. Before a future live rollout, hold and review old/stale jobs, permissions/opt-outs and ambiguous send outcomes.
* Access to every test API requires an Admin/SuperAdmin bearer token and either a genuine loopback connection or HTTPS. The default school LAN HTTP URL is intentionally refused. Open the admin app on the server PC, or independently configure properly trusted HTTPS. Do not expose an HTTP reverse proxy that forwards remote requests to localhost. Protect the admin password and existing JWT configuration.
* The gateway binds only to `127.0.0.1`, requires a random per-process secret held by the API, rejects browser-origin requests, and does not print/log the QR, messages or phone numbers. It does not subscribe to incoming chats or persist chat/history. Baileys needs initial protocol bootstrap for ID mappings; full/recent history is not requested or retained by this application.
* Session/Signal data is encrypted with AES-256-GCM. On Windows the master key is protected by DPAPI for the Windows account running the API; files are under `%LOCALAPPDATA%\SmartSchool\whatsapp-qr-test`. A different Windows login cannot use that key. The API's existing startup shortcut runs under the interactive user, so keep the same server Windows account logged in. On non-Windows test hosts the key is instead protected by local filesystem permissions, not DPAPI.
* The source is independently implemented against MIT-licensed Baileys `7.0.0-rc14`; the supplied kit is not run or redistributed. The Windows build includes Node `22.22.3`, its license, and locked npm dependencies. This is a release-candidate unofficial library: maintenance/security review is needed before any production use.

## Test on a separate, clean Windows PC

1. Use the non-production preview on a separate clean Windows PC/database. Never install it over the live school server. The preview includes the API's .NET runtime, Node, npm dependencies and the SQL LocalDB installer; it starts the test API automatically. See the queue warning above.
2. Log in to the admin app on that PC as Admin or SuperAdmin. Open **WhatsApp Test**. Check the risk acknowledgement, click **QR test shuru karein**, and confirm. A fresh QR is displayed only after this action, and expires if left unattended.
3. On the separate test sender's phone, open WhatsApp → **Linked devices** → **Link a device**, and scan the QR shown on the server PC. Never send a QR screenshot, one-time code, token, session files or key to anyone. The account may disconnect, so monitor the status.
4. Enter a separate test recipient in international form such as `+923001234567`, confirm that you own it or have the recipient's permission, and send one sample pick-in and one sample drop-out. Check the recipient phone manually. No actual parent/attendance event is delivered by this stage.
5. **Submitted** means the library accepted the attempt, not that the phone received or read it. If the result is **unknown**, inspect the phone before another manual attempt; there is no blind automatic retry. Request IDs only deduplicate while that gateway process is alive; exactly-once delivery is not guaranteed.
6. Use **Test session unlink / reset** when finished. Check the phone's Linked devices list and remove the device there if needed. Local encrypted credentials are removed; if WhatsApp was offline the server cannot guarantee the phone was remotely unlinked.
7. Only after the separate-number test succeeds and the owner explicitly approves a rollout should production integration be designed and reviewed. That future stage must prevent old/stale queue release, enforce opt-out/consent, distinguish submitted/sent/delivered/unknown, and handle ambiguous outcomes without blind retries.

## Development and packaging

Node 22: `npm ci --ignore-scripts --omit=dev` and `npm test` in `apps/whatsapp_gateway`. Tests use fake sockets and an inert process, and do not connect an account. CI also runs Windows tests for DPAPI, .NET security tests, and API role/consent smoke checks. On a Windows build host with Node v22.22.3, `scripts/package-whatsapp-qr.ps1` installs locked dependencies, runs tests, and copies only the runtime, source and dependencies into the API payload. No linked session or Firebase credential is packaged. Both preview and future release installer jobs invoke it. No test proves actual WhatsApp pairing/delivery; that requires the owner's separate test phones and consent.
